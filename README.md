# sdtmrag

RAG по документации CDISC SDTM / SDTMIG. Локальные эмбеддинги и реранк (ONNX), генерация ответов через DeepSeek API, CLI + REST API.

Задача проекта — отвечать на вопросы по стандарту SDTM и руководству по внедрению
SDTMIG (в том числе по домену лабораторных исследований LB) со ссылками на
исходные документы. Отдельное внимание уделено двум вещам, от которых в таких
системах зависит почти всё: **качеству текста, извлекаемого из PDF**, и
**измеримости качества поиска и ответов**.

## Требования

- Rust 1.85+ (крейт использует редакцию 2024)
- Windows / Linux (проверено на Windows)
- ~2 ГБ свободного места для ONNX-моделей (автоматически скачиваются при первом запуске)

## Исходные документы

Репозиторий **не содержит** документов CDISC: они распространяются по лицензии
CDISC и не могут быть включены в публичный репозиторий. Перед первым запуском
скачайте с [cdisc.org](https://www.cdisc.org/standards/foundational/sdtm) и
положите в `dicts/`:

| Файл | Где взять |
|---|---|
| SDTM v2.1 (Final) — PDF | раздел SDTM → версия 2.1 |
| SDTM_v2.1.xlsx | там же, табличные определения переменных |
| SDTMIG v3.4 (Final) — PDF | раздел SDTMIG → версия 3.4 |
| SDTMIG_v3.4.xlsx | там же, определения переменных доменов |

Каталог `dicts/` исключён из Git (`.gitignore`), поэтому ваши копии документов
не попадут в репозиторий. Поддерживаются также любые другие `.pdf`/`.xlsx` —
конвейер не привязан к этим четырём файлам.

## Быстрый старт

```bash
# собрать
cargo build --release

# положить документы в dicts/ (см. раздел «Исходные документы»)

# посмотреть, что даёт очистка PDF-текста (индекс не строится)
cargo run --release -- clean

# построить индекс ( ~10-15 мин при ~8 ch/s на слабом ПК )
cargo run --release -- index --rebuild

# найти ответ
cargo run --release -- query "What is SUPPQUAL used for?" --no-generate --top-k 3

# оценить качество по эталонному набору
cargo run --release -- eval --gold eval/gold.en.jsonl --gold eval/gold.ru.jsonl \
    --store data/index_clean.sqlite=baseline --k 1,3,5,10

# или собрать с REST API
cargo build --release --features server
cargo run --release --features server -- serve
```

## CLI

Глобальные опции: `--config <path>` (по умолчанию `config.toml`, если есть) и
`--store <path>` (переопределяет путь к индексу).

### `index`

Построить или пересобрать индекс из файлов в `inputs` (по умолчанию `dicts/`).

```bash
sdtmrag index                    # инкрементальный (если индекса нет — полный)
sdtmrag index --rebuild          # удалить старый и построить заново
sdtmrag index --inputs path/to   # указать директорию
```

Прогресс эмбеддинга выводится в stderr каждые 128 чанков. В конце печатается
статистика очистки текста.

### `clean`

Показывает эффект очистки PDF-текста, не строя индекс. Полезно при подборе
правил очистки под новый документ.

```bash
sdtmrag clean                          # сводка по каждому PDF
sdtmrag clean --json                   # та же сводка в JSON
sdtmrag clean --out data/cleaned       # выгрузить очищенный текст постранично
sdtmrag clean --limit 1                # только первый файл
```

### `query`

Поиск по вопросу: retrieval -> реранк -> генерация.

```bash
sdtmrag query "How to create a SUPPQUAL dataset?"
sdtmrag query "Define LBORRES" --top-k 3 --no-generate   # без генерации, только retrieval
sdtmrag query "STUDYID" --no-rerank --json               # косинусный поиск без реранка
```

### `eval`

Оценка качества по «золотому» набору вопросов (см. раздел «Оценка качества»).

```bash
# сравнить несколько индексов в одном отчёте
sdtmrag eval --gold eval/gold.en.jsonl \
    --store data/index_raw.sqlite=raw \
    --store data/index_clean.sqlite=clean \
    --store data/index_clean_tuned.sqlite=clean+tuned \
    --k 1,3,5,10 --out eval/reports

# добавить оценку ответов LLM-судьёй (нужен DEEPSEEK_API_KEY)
sdtmrag eval --gold eval/gold.en.jsonl --store data/index_clean.sqlite=clean --judge
```

Отчёт пишется в `eval/reports/<дата>/{report.json,report.md}` и дублируется в stdout.

### `stats` / `list-docs`

```bash
sdtmrag stats       # количество чанков, метаданные сборки, список источников
sdtmrag list-docs   # файл + количество чанков на каждый источник
```

### `serve`

REST API (axum). С feature `server`.

```bash
sdtmrag serve                        # 127.0.0.1:8080
sdtmrag serve --bind 0.0.0.0 --port 9090
```

## Очистка PDF-текста

`pdf-extract` отдаёт «сырой» поток, непригодный для эмбеддинга. На корпусе из
двух PDF (545 страниц) замерено:

| Проблема | Проявление |
|---|---|
| Колонтитулы внутри строк | `... CRF  nsortium, Inc. All rights reserved  Page 258 2021-11-29 The SUPPBE dataset ...` — копирайт, номер страницы и дата выпуска склеены с содержательным текстом |
| Схлопнутые таблицы | столбцы разделены сериями пробелов: `2  ABC  BE  ABC-01-101  BEREFID ...` |
| Оглавление в потоке | строки вида `1.1  PURPOSE .............. 5` попадают в текст как обычные строки |
| Разорванные переносы | `impl-` + `ementation` |
| Типографика | лигатуры, тире `–`, кавычки `“ ”`, неразрывные пробелы, soft hyphen |

Модуль `src/clean.rs` устраняет всё перечисленное:

1. **Нормализация Unicode** — лигатуры (`ﬁ` → `fi`), тире и кавычки → ASCII,
   удаление `©`/`®`/`™`, nbsp, soft hyphen и символов-заместителей.
2. **Inline-чистка** — регулярные выражения удаляют колонтитулы, *вклеенные внутрь*
   содержательных строк (основной источник мусора: ~68 тыс. символов на корпусе).
3. **Отсев колонтитулов-строк** — копирайты, чистые номера страниц, ISO-даты
   выпуска, бегущие заголовки стандарта.
4. **Удаление повторяющихся строк** — строка, встретившаяся не менее чем на
   `boilerplate_min_pages` страницах или на `boilerplate_page_ratio` доле страниц,
   остаётся только в первом вхождении (снимает повторяющиеся шапки таблиц).
5. **Отсечение оглавления** — строки с точечными выносками и заголовки CONTENTS.
6. **Дегисфенация** — склейка слов, разорванных переносом. Решение принимается по
   словарю корпуса: если дефисная форма встречается в тексте как обычное слово
   (`non-standard`), а слитная — нет, дефис сохраняется; иначе слово склеивается.
7. **Разметка табличных строк** — строки с двумя и более разрывами из 2+ пробелов
   переразмечаются в `a | b | c`, что не даёт табличным строкам притворяться
   заголовками разделов и сохраняет границы ячеек для эмбеддинга.

Замеренный эффект на текущем корпусе: 46 019 → 31 260 строк (−32%),
2 007 379 → 1 813 627 символов (−9.7%), из них 67 964 символа — колонтитулы
внутри строк, 8516 табличных строк переразмечено, 817 строк-колонтитулов,
1612 повторов, 329 строк оглавления, 212 склеек переносов.

Чанкер дополнительно проверяет, что заголовок раздела — это действительно
заголовок: отвергаются строки со `|`, с точечными выносками и с двумя и более
разрывами из 2+ пробелов. До этой проверки 73% чанков PDF получали в качестве
раздела строку таблицы или оглавления (`1 | Role | CDISC Notes | Core`,
`456 | CP | 0001`), из-за чего метаданные раздела были бесполезны.

## Оценка качества

### Эталонный набор

`eval/gold.en.jsonl` (71 вопрос) и `eval/gold.ru.jsonl` (25 вопросов) — по одному
JSON-объекту на строку:

```json
{
  "id": "en-lb-05",
  "question": "What does the variable LBORRES represent in the LB domain?",
  "lang": "en",
  "topic": "LB",
  "answerable": true,
  "expected": [{"source": "SDTMIG_v3.4.xlsx", "sheet": "Variables", "row": 892}],
  "reference_answer": "Result or Finding in Original Units (Char, role: Result Qualifier). ...",
  "needs_review": true,
  "notes": "auto: SDTMIG_v3.4.xlsx Variables row 892 (LB domain)"
}
```

Локатор — это *место в документе*, а не конкретный чанк: файл плюс страница,
раздел или лист+строка Excel. Благодаря этому один и тот же набор применим к
индексам с разным чанкингом, а метрики не зависят от того, как нарезан текст.
Сравнение локаторов устойчиво к регистру, пробелам и типографике, поэтому
работает и на «сыром», и на очищенном индексе.

Состав набора:

| Тема | Вопросов | Источник эталона |
|---|---:|---|
| LB (переменные домена лабораторных исследований) | 36 | SDTMIG v3.4, лист Variables |
| Общая модель SDTM | 17 | SDTM v2.1, лист Variables |
| Разделы PDF | 25 | SDTMIG v3.4 / SDTM v2.1 |
| Структура наборов данных | 11 | SDTMIG v3.4, лист Datasets |
| Вне области документации (`answerable: false`) | 7 | — |

Вопросы с `needs_review: true` сгенерированы автоматически по определениям
CDISC и требуют проверки экспертом; вопросы по разделам PDF сформулированы
вручную. Корректность каждого локатора проверена программно: он обязан
пересекаться хотя бы с одним чанком индекса.

### Метрики

Retrieval (считаются офлайн, без обращений к API):

- **Hit@k** — доля вопросов, для которых в топ-k есть хотя бы один верный фрагмент;
- **Recall@k** — доля закрытых эталонных локаторов;
- **Precision@k** — доля релевантных чанков в топ-k;
- **nDCG@k** — с бинарной релевантностью, учитывает позицию верного фрагмента;
- **MRR** — обратный ранг первого верного фрагмента;
- задержка ответа (mean / p50 / p95 / max).

Метрики разбиваются по языку вопроса и по теме.

Ответы (только с флагом `--judge`, требуется `DEEPSEEK_API_KEY`) — LLM-судья
выставляет оценки от 0 до 1:

- **faithfulness** — доля утверждений ответа, подтверждённых выданными выдержками;
- **citation_accuracy** — соответствие ссылок `[1]`, `[2]` тем выдержкам, к которым они привязаны;
- **correctness** — согласие с эталонным ответом; для вопросов вне документации
  верным считается явный отказ отвечать;
- **refusal_correct** — правильно ли система отказалась отвечать.

### Абляции

Готовые конфигурации для сравнения лежат в `eval/configs/`:

| Конфиг | Очистка | Чанкинг | Что изолирует |
|---|---|---|---|
| `raw.toml` | выключена | `target_tokens = 900` | базовая линия на сыром тексте |
| `clean.toml` | включена | как в `raw.toml` | эффект очистки текста |
| `clean_tuned.toml` | включена | `target_tokens = 400`, `min_chunk_chars = 600` | эффект подгонки чанка под окно энкодера |

```bash
for c in raw clean clean_tuned; do
  sdtmrag index --rebuild --config eval/configs/$c.toml
done

sdtmrag eval --gold eval/gold.en.jsonl --gold eval/gold.ru.jsonl \
  --store data/index_raw.sqlite=raw \
  --store data/index_clean.sqlite=clean \
  --store data/index_clean_tuned.sqlite=clean+tuned
```

Индекс хранит собственные метаданные (модель эмбеддинга, размерность векторов,
параметры чанкинга и очистки, статистику очистки, список исходных файлов),
поэтому при оценке и при поиске модель берётся из индекса, а не из текущего
конфигурационного файла, а `sdtmrag stats` показывает происхождение каждого
индекса. Если размерность вектора запроса не совпадает с размерностью векторов
индекса, поиск завершается явной ошибкой — иначе сравнение векторов разной длины
дало бы тихо неверный результат.

Индексы, используемые в отчётах:

| Файл | Что это |
|---|---|
| `data/index_clean.sqlite` | лучшая измеренная конфигурация (очистка включена); используется по умолчанию |
| `data/index_raw.sqlite` | очистка выключена — базовая линия |
| `data/index_clean_tuned.sqlite` | очистка + чанк под окно энкодера |
| `data/index_clean_e5.sqlite` | очистка + многоязычная multilingual-e5-small (кросс-язычный срез) |
| `data/index_legacy.sqlite` | сборка до исправления заголовков разделов (6296 чанков); сохранена как точка отсчёта |

## Конфигурация

Скопируйте `config.toml.example` в `config.toml`. Все параметры опциональны
(есть дефолты). Описание секций — в самом файле.

## Архитектура

```
dicts/*.pdf,*.xlsx
       |
    extract       pdf-extract (постранично) / calamine (по строкам)
       |
     clean        удаление колонтитулов, оглавления, повторов; дегисфенация;
                  нормализация Unicode; разметка табличных строк   (src/clean.rs)
       |
     chunk        PDF: regex по секциям + проверка заголовка, склейка коротких
                  чанков; XLSX: по строкам
       |
     embed        fastembed (ONNX) -> нормализованные f32-векторы, dim=384
       |
     store        SQLite: chunks(source, kind, page, section, sheet, row, text,
                  embedding BLOB) + meta (происхождение индекса)
       |
    query        cosine brute-force -> top candidates -> cross-encoder rerank -> context
       |
  generate       DeepSeek API (chat completions)
       |
     eval        локаторы -> Hit@k / Recall@k / nDCG@k / MRR (+ LLM-судья)
```

## Модели (автозагрузка)

| Компонент    | Модель по умолчанию  | Размер | Другие варианты                          |
|-------------|---------------------|--------|------------------------------------------|
| Эмбеддинг   | bge-small-en-v1.5   | ~130 MB| bge-base-en-v1.5, bge-large-en-v1.5, bge-m3, multilingual-e5-small/base/large, paraphrase-multilingual-minilm-l12-v2, all-minilm-l6-v2 |
| Реранк       | bge-reranker-base   | ~1.1 GB| bge-reranker-v2-m3, jina-reranker-v1-turbo-en |

Модели скачиваются в `models/` при первом использовании.

Префиксы инструкций подставляются автоматически: для семейства bge — инструкция
поиска к запросу, для семейства E5 — `query: ` к запросу и `passage: ` к
документам (без них качество поиска у E5 заметно падает).

**Ограничения моделей, которые важно учитывать.**

* bge-small-en-v1.5 обучена на английском и читает не более 512 токенов
  (~2000 символов). Чанк длиннее окна молча обрезается при эмбеддинге — при
  индексации выводится предупреждение, если `target_tokens * 4` превышает окно.
  Для русскоязычных вопросов нужна многоязычная модель.
* bge-m3 в fastembed поставляется как fp32 ONNX (~2.2 ГБ, 568M параметров) и на
  CPU даёт около 0.04 фрагмента/с, то есть ~23 часа на корпус из 3418 фрагментов.
  Для многоязычного поиска на CPU практичнее `multilingual-e5-small`
  (118M параметров, 384 измерения) или `paraphrase-multilingual-minilm-l12-v2`.
* Число потоков и размер батча задаются в `[embedding]` (`intra_threads`,
  `batch_size`); для крупных моделей батч следует уменьшать.

## Производительность

Замеры на настольном CPU (8 логических ядер, `intra_threads = 4` для
эмбеддинга), без изоляции от других процессов:

| Конфигурация | Чанков | Индексация | Размер индекса | Поиск (p50) |
|---|---:|---:|---:|---:|
| `raw` (без очистки) | 3461 | 22,5 мин | 10,6 МБ | 80 мс |
| `clean` | 3418 | 15,8 мин | 10,3 МБ | 68 мс |
| `clean+tuned` | 4111 | 41,6 мин | 12,2 МБ | 65 мс |

Поиск без реранка — десятки миллисекунд. **Реранк на порядки дороже**: при 20
кандидатах и длине пары «запрос + фрагмент» 256 токенов — около 18 с на запрос,
при 50 кандидатах и 512 токенах — около 130 с. Причина в том, что стоимость
кросс-энкодера линейна и по числу кандидатов, и по длине фрагмента, а
bge-reranker-base — это модель на 110 млн параметров, считающаяся на CPU.
Для интерактивной работы реранк необходимо ограничивать
(`rerank.candidates`, `rerank.max_length`) либо выносить на GPU.

## Результаты оценки

Оценка на 89 ответимых вопросах эталонного набора, без реранка
(`eval/reports/`):

| Конфигурация | Hit@1 | Hit@5 | Recall@5 | nDCG@5 | MRR |
|---|---:|---:|---:|---:|---:|
| `raw` | 0,427 | 0,730 | 0,730 | 0,582 | 0,545 |
| `clean` | 0,461 | **0,775** | **0,775** | **0,624** | **0,584** |
| `clean+tuned` | **0,472** | 0,719 | 0,719 | 0,601 | 0,577 |

Очистка текста даёт статистически различимый прирост (парный bootstrap:
Recall@5 +0,045 [0,011; 0,090], nDCG@5 +0,042 [0,006; 0,086]). Подгонка размера
чанка под окно энкодера значимого выигрыша не дала. По языку вопроса разрыв
почти двукратный: Recall@5 = 0,879 для английских вопросов против 0,478 для
русских — следствие одноязычной модели эмбеддингов.

Замена модели на многоязычную (те же корпус, очистка и чанкинг) подтверждает
это и устраняет разрыв примерно наполовину (`eval/reports/multilingual/`):

| Модель эмбеддингов | Recall@5 (en) | Recall@5 (ru) | MRR (ru) | MRR (всего) |
|---|---:|---:|---:|---:|
| bge-small-en-v1.5 | 0,879 | 0,478 | 0,297 | 0,584 |
| multilingual-e5-small | **0,894** | **0,696** | **0,568** | **0,655** |

Для русских вопросов выигрыш значим (Hit@1 +0,304 [0,130; 0,478], МакНемар
p = 0,0156; nDCG@5 +0,260 [0,082; 0,441]), английские вопросы не ухудшаются.

Влияние реранка (89 ответимых вопросов, 20 кандидатов, 256 токенов): Recall@5
растёт с 0,730 до 0,820 (`raw`), с 0,775 до 0,854 (`clean`) и с 0,719 до 0,798
(`clean+tuned`); nDCG@5 — на +0,066…+0,094; улучшается и первая позиция
(Hit@1 0,461 → 0,539 для `clean`). То есть кросс-энкодер не только добавляет
полноты, но и точнее ранжирует найденное, однако стоит на три порядка больше
времени, чем векторный поиск.

Оценка ответов LLM-судьёй (48 вопросов, `clean+tuned`): faithfulness 0,999,
citation accuracy 0,998, correctness 0,979, корректных отказов 4 из 4. Система
не выходит за пределы выданных фрагментов и отказывается отвечать на вопросы вне
документации.

Полные отчёты (`report.json` и `report.md`) лежат в `eval/reports/`; для
доверительных интервалов и парных тестов служит `eval/analyze.py`:

```bash
python eval/analyze.py --pair clean:raw --pair clean+tuned:clean \
    eval/reports/rerank/<дата>/report.json

# сравнение прогонов на общей подвыборке
python eval/analyze.py --only-gold eval/gold.judge.jsonl \
    eval/reports/norerank/<дата>/report.json eval/reports/judge/<дата>/report.json
```

### Экспертная валидация

Оценка LLM-судьёй и эталонный набор построены авторами системы; для публикации
результатов нужна независимая проверка специалистами. Таблица для неё готовится
скриптом, инструкция для эксперта — в `eval/examples/review_instructions.md`:

```bash
python eval/make_review_sheet.py \
    eval/reports/judge/<дата>/report.json \
    --gold eval/gold.en.jsonl --gold eval/gold.ru.jsonl \
    --out eval/review_sheet.csv --limit 25
```

Примеры реальных обращений к системе (успешный ответ, ложный отказ из-за
кросс-язычного провала поиска, корректный отказ) разобраны в
`eval/examples/clinical_examples.md`.
